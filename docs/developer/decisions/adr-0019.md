# ADR-0019 — Where the field Pi stops being Docker

**Status:** accepted
**Date:** 2026-08-26
**Context:** field host (Raspberry Pi 5) running the LoRaWAN stack with a
Kerlink iFemtoCell Evolution attached over USB.

## Question

Can the field host be a "pure Docker" setup — and if the gateway hangs on
USB, does it need device passthrough into a container?

## Decision

**No, and no.** The application stack stays fully containerised, the
firmware, kernel and network-interface layer stays on the host, and the
boundary between them does not move. USB passthrough is not merely
unnecessary here — it does not apply.

## Why passthrough does not apply

The gateway is **not a serial device**. It enumerates as a USB Ethernet
gadget and the kernel binds `cdc_eem` to it:

```
Bus 001 Device 019: ID 0525:a4a2 Linux-USB Ethernet/RNDIS Gadget
/sys/class/net/usb0/device/driver -> cdc_eem
```

There is no `/dev/ttyUSB*` or `/dev/ttyACM*` to hand to a container —
verified on the host, none exists. What the kernel produces is a **network
interface**, `usb0`. Containers reach networks through ordinary port
publishing, which is exactly what happens today: `docker-proxy` holds
`0.0.0.0:1700/udp` and forwards to the gateway bridge.

Consequently `docker-compose.yml` contains no `privileged`, no `devices:`,
no `cap_add` and no `network_mode: host`. Every service runs unprivileged
on the default bridge network. That is not an accident to be improved on;
it is the correct shape for this hardware.

## What must stay on the host, and why

**Firmware — cannot be containerised at all.** `/boot/firmware/config.txt`
is read by the bootloader long before Docker exists:

| Setting | Consequence if absent |
|---|---|
| `usb_max_current_enable=1` | The Pi 5 caps total USB draw at 600 mA and the gateway browns out under load. Needs a ≥27 W supply alongside. |
| `dtoverlay=dwc2,dr_mode=host` | The USB controller never enters host mode and `usb0` never appears. |

**Kernel.** `cdc_eem` creates `usb0`. A container cannot create an
interface the kernel has not.

**Network configuration.** The NetworkManager profile `kerlink-usb`:

```
ipv4.method manual · 192.168.120.31/24
ipv4.routes 169.254.0.0/16 · ipv4.never-default yes
ipv6.method disabled · autoconnect yes
```

Two details here are easy to lose and expensive to debug:

- **The link-local route is load-bearing.** The gateway sends from
  `169.254.x.x`, not from `192.168.120.x` — confirmed by packet capture:
  `169.254.82.2.38343 > 192.168.120.31.1700`. Without `169.254.0.0/16` on
  `usb0` the return path is dead while every interface still looks up.
- **`never-default: yes`** keeps a point-to-point link from claiming the
  default route and taking the host off the internet. This is the same
  failure class as the WireGuard `AllowedIPs` trap this host already fell
  into once (see `host-setup.sh` step 6).

WireGuard and the eduroam profile are host configuration for the same
reason.

## Could the host part be containerised anyway?

Technically yes: `network_mode: host` plus `NET_ADMIN` would let a
container run `nmcli`. That trades a documented host configuration for a
privileged container that configures the host — Docker in name only, and
harder to reason about, not easier. Rejected.

## Evidence the split works

The stack has been up **3 weeks 4 days** since the 2026-08-01 boot, all
seven containers healthy, `kerlink-usb` set to `autoconnect: yes` so the
link returns by itself after a reboot. The full path was traced live on
2026-08-26:

| Hop | Verified by |
|---|---|
| gateway → Pi | `tcpdump` on `usb0`, UDP 1700 both directions every 10 s |
| host → container | `docker-proxy` on `0.0.0.0:1700/udp` |
| bridge → MQTT | `eu868/gateway/<eui>/event/stats` and `state/conn` observed |
| MQTT → ChirpStack | gateway `last_seen_at` 23 s old |
| MQTT → cockpit | ingest subscribed to the application and gateway topics |

## Consequence

The real gap was never the architecture — it was reproducibility.
`scripts/host-setup.sh` covered the journal, Docker log rotation, cgroups,
`fake-hwclock`, Wi-Fi power save and WireGuard, but **not** the two things
without which no byte arrives: the `kerlink-usb` profile and the firmware
settings. Both are now steps 7 and 8, idempotent and with a `--check` mode,
so a rebuilt host is fully described rather than two thirds described.

Verified against the live host in both directions: it reports `ok` for the
configured state, and reports the missing item for a deliberately wrong
profile name, a wrong expected route and a wrong firmware line.
